# 共有経路の同一性と生成コストを比較する

同じ木を共有方式と再計算方式で再生し、生成データと学習上の重みを検証してから、共有経路の再利用による生成コストの差を比較します。学習更新や対戦評価は行いません。

## CPU・MPSで実行する

通常版CPython 3.14、uv、Rust toolchainを用意し、パッケージのディレクトリで実行します。

```sh
uv sync --locked
mkdir -p artifacts
uv run --locked lfu-tree-self-play verify-shared-paths --device cpu --output artifacts/h1-cpu.json
uv run --locked lfu-tree-self-play verify-shared-paths --device mps --output artifacts/h1-mps.json
```

MPSの実行には対応したMacとPyTorchが必要です。指定したdeviceが使えない場合やメモリ上限を超えた場合は、失敗のレポートを残します。deviceの代替や上限の自動変更は行いません。

成功すると`PASS`と保存先を表示し、終了コード0を返します。同一性の不一致や計測失敗は`FAIL`・終了コード1になります。出力先へ書き込めない場合は終了コード2です。

既定の比較は幅64・残差4ブロックの固定モデルを使い、3 seed × 4根から幅4・2段の木を生成します。両方式のbatch上限は32、同時単位上限は32、RSS・deviceの上限はそれぞれ2 GiBです。各方式を別プロセスでウォームアップ1回後に計測し、順序を交互にして3回繰り返します。使用したseedと設定はJSONレポートに記録します。モデルや木の準備にも時間がかかります。

## 何を再計算するか

同じ完成済みの木と抽選結果を入力に使います。共有方式は共通経路の計算を共有し、再計算方式は終局葉ごとに根から全経路を再実行します。両方式から同じ学習データを構成し、計算の重複だけを比較します。再生の定義と数値の一致条件は[T17の正本](../development/milestones/02-collection.md#t17-共有あり再計算の同一性とh1計測)を参照してください。

## レポートを読む

生成時間には再生の推論・環境遷移・木の組み立て・schedulerの待機と管理を含めます。モデルロード、参照木の準備、再生入力の検証、完成後の検証・リターン集約、保存は含めません。検証処理も盤面遷移を再生するため、生成の遷移数と混ぜないよう計測を分離しています。

生成中に行う固定経路との整合性確認は管理費用に含みます。完成後の全件検証と出力同士の比較は、生成時間の計測後に行います。

推論件数は実際に推論した盤面数とbatch数を分けて確認します。単位ごとの推論回数を合計して物理batch数として扱わないでください。共通経路の節約は盤面数と環境遷移数で確認できても、batch効率や木の管理費用によって実時間の差は変わります。

RSSは計測区間の標本ピーク、deviceメモリは別のピーク値として記録します。モデルと固定入力の保持を含むプロセスのメモリであり、生成による増加量そのものではありません。RSSの標本間の瞬間的なピークは保証せず、上限もOSによる強制上限ではありません。CPUのdeviceメモリは`null`です。

結果は同じマシン・device・モデル・設定の組で比較します。短縮がなくても観測結果として残し、この比較から独立自己対戦に対する棋力の優位性や、学習を含めた総コストの改善を結論しません。
