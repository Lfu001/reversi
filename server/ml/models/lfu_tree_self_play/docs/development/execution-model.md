# 実行モデル

[← 一覧](README.md) · [実験計画](../research/experiment-plan.md) · [検証ゲート](verification-gates.md)

研究計画を実装するときの処理の流れと確定境界を定義します。学習・対戦評価を含む一巡実行は開発対象です。現在利用できる収集・保存・復元の手順は [パッケージの README](../../README.md) から参照してください。

## 通常フロー

1. 設定内容とseed集合からexperiment IDを確定します。
2. ラウンド開始時のcheckpointをπ_oldとして固定してデータを収集します。
3. 完了データを検証し、atomicにdatasetへ公開します。
4. manifestで固定したデータを [実験計画の更新条件](../research/experiment-plan.md#43-方策更新と共有経路の重み) に従って学習し、新しいcheckpointを確定します。
5. 確定checkpointだけを調整用集合で評価します。
6. 累積収集・学習時間が評価境界へ達した後の最初の安全な更新境界で保存・評価します。
7. 最終評価集合はモデル選択やハイパーパラメータ調整に使用しません。

## 再開単位

- Aの収集は、終局まで完了した対局を公開単位とします。
- B/Cの収集は、全枝が終局した木を公開単位とします。
- 学習は、入力manifestと設定に結び付けて、モデル、optimizer・scheduler、RNG、データ消費位置を一体で確定します。モデル世代、処理段階、累積計算コストも同じ checkpoint に含め、状態と進捗の不一致を防ぎます。
- 評価は、checkpoint、相手、開始局面ペア、seedを再実行単位とします。
- 集計は原結果を変更せず、派生成果物として何度でも再生成できるようにします。

モデルと入力の消費位置を同じ checkpoint で確定するのは、モデルだけが更新されることや、更新が未確定なのに入力だけが消費済みになることを防ぐためです。復旧後もこの対応を保ち、未確定の更新だけをやり直します。

## 保存基盤と適用条件

現在の dataset と checkpoint の保存基盤は、一時領域への書込みと検証を経て atomic rename で公開・確定します。`flock` と `fsync` を利用できる POSIX ローカルファイルシステムを前提とします。利用時の制約と復元方法は [復旧ガイド](../guides/recovery.md#復旧できない場合) を参照してください。

## 乱数とモデル世代

- 分岐位置抽選、行動抽出、兄弟の継続試行、評価には別々のRNG系列を使用します。
- 収集ラウンド中にモデルを更新しません。
- datasetは生成したモデル世代を必ず保持します。
- 保存されている古い木と、現在の方策更新に利用可能な木を区別します。

## 障害時の扱い

- 収集中断：完成済み対局・木だけを再利用し、未完成単位を破棄します。
- 公開中断：一時領域のデータを不可視のまま残し、検証後にだけ公開します。
- 学習中断：直前の確定checkpointへ戻し、未確定の消費記録を無効化します。
- 評価中断：同じcheckpointとseedで、未完了の開始局面ペアだけを再実行します。
- 集計中断：原結果を変更せず、集計物だけを再生成します。
- 設定不一致：自動補正せず実行を拒否します。

## 予算と評価境界

- 収集途中の木や対局、optimizer stepの途中では停止しません。
- 進行中単位の完了による予算超過を実コストへ含めます。
- [実験計画の評価間隔](../research/experiment-plan.md#6-計算量棋力統計) に達した後の最初の安全な更新境界で保存・評価します。実際の保存時刻を使って、同じ節で定める検出到達時間を算出します。
- 学習中も時間または更新数を基準に、安全な更新境界で定期保存できるようにします。

個々の実装・実験タスクは[開発段階の一覧](README.md#開発段階)から参照してください。
